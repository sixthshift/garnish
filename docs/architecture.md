# Architecture

How garnish is built. Decisions and their alternatives are in [decisions.md](decisions.md); what ships when is in [scope.md](scope.md).

## Shape

- One Bun process. TanStack Start on Nitro's Bun preset serves the app, server functions and `/api/*` routes. The server entry (`src/server.ts`) creates `DATA_DIR`, opens, migrates and seeds the database before the first request, so a broken volume fails the start, not a user.
- One SQLite file. `bun:sqlite`, WAL mode, foreign keys on.
- One Docker container. The SQLite file lives on a mounted volume.
- LAN only. No auth, no users, no accounts.

```
browser (PWA) ──server fns / HTTP──▶ TanStack Start (Nitro, Bun) ──▶ bun:sqlite ──▶ garnish.db (volume)
```

## Stack

| Layer | Choice |
|---|---|
| Runtime | Bun 1.4 or newer (1.3 cannot parse the built server, decisions.md row 32) |
| Framework | TanStack Start in SPA mode, in production as in dev: every page request gets the shell and the browser draws the page (`TSS_SHELL`, set in `src/server/shellMode.ts`; decisions.md row 169), as Mealie, Tandoor, Sonarr and Radarr do. Routes declared in code in `src/routes/`, pages in each section's `src/domain/<section>/pages/` |
| Build | Vite via `bun --bun vite`, `NODE_ENV=production` set by the build script; Nitro Bun preset for production; the service worker is emitted by a small Vite plugin in the client build |
| Frontend | React 19 + Tailwind 4 via `@tailwindcss/vite` |
| UI kit | `@sixthshift/design-system`, subpath imports (`sheet`, `toast`, `popover`, `tabs`, `search-input`, `switch`, `badge`, `tooltip`, `modal`). Gaps built locally from its primitives under `src/components/ui/`: `Rating`, `NumberStepper`, `ReorderList`, `ImageUpload`, `ConfirmDialog`, `UsageConfirmDialog`, `Menu`, `DataTable`, `EditSheet`, `BulkAddSheet`, `SaveBar`, `Disclosure`, `EditorToolbar` |
| Storage | SQLite (`bun:sqlite`) |
| Queries | Drizzle ORM over that same `bun:sqlite` handle; tables in `src/db/models/<domain>/schema.ts` (decisions.md row 46) |
| Validation | zod, one schema per document, shared by API and editor |

## Data model

Mealie's schema outside recipe internals, minus users and groups. Tandoor's shape inside recipes. When a field is in doubt, Mealie wins.

```
recipe        id, slug, name, description, image, rating, last_made, favourite,
              servings, yield_quantity, yield_unit_id?, yield_text,
              prep_minutes, cook_minutes, source_url, created_at, updated_at
recipe_note   id, recipe_id, position, title, text
timeline_event id, recipe_id, occurred_on, message, image, created_at
part          id, recipe_id, position, name
ingredient    id, part_id, position, quantity?, unit_id?, food_id?,
              note, original_text, fixed, quantity_max?
step          id, part_id, position, text, image?
step_ingredient step_id, ingredient_id, position
food          id, name, plural_name, aliases, aisle_id?, recipe_id?, skip_shopping
food_conversion id, food_id, unit_id, quantity, to_unit_id, to_quantity
food_pack     id, food_id, quantity, unit_id?
alternative   id, ingredient_id, position, basis_quantity?, basis_unit_id?,
              note, plan_picks
alternative_item id, alternative_id, position, food_id, quantity?, unit_id?
aisle         id, name, position
unit          id, name, plural_name, abbreviation, use_abbreviation, fraction,
              standard_quantity?, standard_unit_id?, portion
tag           id, name, slug
recipe_tag    recipe_id, tag_id
recipe_facet  recipe_id, layer, value
shopping_item id, position, food_id?, unit_id?, quantity?, text, ticked,
              created_at, updated_at
shopping_item_source id, item_id, recipe_id?, recipe_name, part_name,
              servings?, quantity?
meal_plan_entry id, date, position, recipe_id?, text, servings?, meal?, choices
style_rule    id, position, text, enabled, created_at, updated_at
migration     id, name, applied_at
```

Ids are UUID text; timestamps are ISO 8601 UTC text. `food`, `unit`, `aisle` and `tag` names are unique case-insensitively. Deleting a recipe cascades to its parts, ingredients, steps, notes, timeline events and tag links; deleting a part cascades to its ingredients and steps; a step link cascades from either side, so deleting a step or an ingredient takes the links naming it; deleting a food, unit or aisle sets the references null. `position` is unique within its parent.

The document the API reads and writes (`src/domain/recipes/recipe/recipe.ts`) mirrors these columns in camelCase, with Mealie's names where Mealie has the concept: `servings` → `recipeServings`, `yield_quantity` → `recipeYieldQuantity`, `yield_text` → `recipeYield`, `prep_minutes` → `prepTime`, `cook_minutes` → `performTime`. The two times are integer minutes, not Mealie's free-text strings (decisions.md row 35). Array order carries `position`, so the document has no position fields. Foreign keys come back as nested objects (`unit`, `food`, `yieldUnit`, `tags`); writes use only the nested `id`. Steps exist only inside `parts`; the document has no recipe-level `steps` array. A step carries `ingredientIds`: the ids of the ingredients it uses, in link order.

- A recipe is an ordered list of parts. Every recipe has at least one; a single unnamed part is the flat case.
- Each part owns its ingredients and its steps. Same food in two parts is two rows.
- Steps link ingredients, many to many, **within one part** (decisions.md row 64). Ownership is the tree; a link is only "this step uses that row". A step may link any ingredient of its own part, and an ingredient may be linked from several of that part's steps. A link across parts is dropped on save rather than failing it — the row belongs in this part, or in the recipe's body. A link carries the whole row: splitting one amount across steps is two rows, not two links.
- The unnamed part (`name = ''`) is the recipe's main body, printed without a heading — so a recipe with one named sub-preparation does not have to invent a heading like "To assemble" for the rest of its method.
- `quantity` null means "no amount" (salt to taste). `fixed` true means "has an amount, does not scale" (one egg wash). Cooklang's `=`. `quantityMax` is a range's upper bound, "5–6 tbsp", above `quantity`; null is one amount. It scales with `quantity`, and the shopping list and a sub-recipe's servings take it, so nothing runs short (decisions.md row 220).
- `food_id` and `unit_id` are nullable. A line that is only text still saves. `original_text` is always kept.
- Servings and yield: `servings` and `yield_quantity` are numbers and scale; `yield_text` is display. Mealie's three fields. `yield_unit_id` lets a parent later ask for "150 ml of this".
- Sub-recipes attach to the **food**, not the ingredient row: `food.recipe_id`. An ingredient line reads "150 g hollandaise" and does not care whether hollandaise has a recipe. Tandoor's shape. A parent scales through it (decisions.md row 70): `subRecipeScale` in `src/domain/recipes/recipe/subRecipe.ts` expresses the row's amount in the child's `yield_unit` — the same unit, or through the food's conversions — and reads off `(amount / yield_quantity) * servings`, null whenever nothing relates the two. That derived figure is the link's hint on the recipe page, cook mode's "Open <child> at N servings", and the servings the shopping sheet fetches the child at. Since the page scales its document before rendering, the parent's own scale flows through. One level only: expanding a child does not expand the child's own sub-recipes, and nothing guards a cycle because nothing recurses. A parent follows its child's yield live, nothing pinned; both stay as they are (decisions.md row 130).
- `favourite` is a 0/1 flag on the recipe, not a magic tag (decisions.md row 43). Which part of the week a recipe fits is the facet layer `week`, `weeknight` and `weekend`, a set like the others (decisions.md row 219, folding in row 191's `kind`, which `035_week_facet.sql` carried across and dropped): set by the household and never inferred, not even by an import; the plan's weeknights come from the weeknight recipes, its weekend from the weekend recipes, each first narrowed to what can be a dinner on its own (`suitsSlot` in `src/domain/plan/plan/slots.ts`: a main, a soup, a salad, or no course said). Beside them, a recipe's **facets** (`recipe_facet`, decisions.md row 209, reversing row 42's "tags are the only organiser"): eight layers, each a fixed list in `src/domain/recipes/recipe/facets.ts` — course (main, side, sauce…), meal (breakfast, lunch, dinner), week (weeknight, weekend), cuisine, diet, main ingredient, method and season — one row a value, every layer a set and empty until said. The document carries them as `facets: { course, meal, week, cuisine, diet, mainIngredient, method, season }`; the table checks the layer and the app checks the value, so a list can grow without a rebuild, and a read drops a value the lists no longer hold. A filter asks any of a layer's values and every layer given. Tags stay for whatever fits no layer; there are no tools. A week is varied by the facets too (decisions.md row 212, `plan/variety.ts`): the weeknights' fill and Swap take no main ingredient two nights running and no cuisine more than twice, and make the vegetarian nights the household asked for (Plan the week's "Vegetarian nights", remembered on the device) on nights spread through the week, each rule giving way only when the library cannot keep it, the cuisine first and the vegetarian nights last; the model is told the same (`varietyLine`).
- Alternatives (decisions.md row 199, `030_alternative.sql`, which replaced rows 196 and 198's tables): what a line can be made with instead. An `alternative` belongs to one ingredient line and cascades from it; its `alternative_item` rows are what goes in, each a food with an amount measured against the alternative's basis (`basis_quantity` of `basis_unit_id`, "per 1 cup"; none is a straight swap, whose own amounts scale with the line, and an item with no amount takes the line's). `plan_picks` marks the ones the plan rotates through, each a single food. Deleting an item's food cascades to the item, and a trigger deletes an alternative left with none; merging foods moves the items and drops a food offered as the alternative to itself. A food has no alternatives of its own. In the recipe document they are the line's `alternatives`; `alternativeText` (`src/domain/recipes/recipe/alternatives.ts`) writes each under the line at its amount on the recipe page and in cook mode. `meal_plan_entry.choices` (JSON, ingredient id to food id) is which food each line takes for that entry; it is JSON rather than a table because a recipe save deletes and re-inserts the recipe's rows, so a foreign key into them would be wiped by every save. The entry also reads `chosen` (the chosen foods' names) and `choosable`. `src/domain/recipes/recipe/choices.ts` holds `withChoices` (the recipe made with them: the server applies it before adding a week to the list, the recipe and cook pages from `?choices=`) and `rotateChoices` (a new entry's choice, the food the recipe's earlier entries used least; `src/server/plan/choices.ts` applies it on add, in Plan the week and from the MCP connector). Backups carry them; Cooklang export drops them.
- `timeline_event` is one logged cook: `occurred_on` is a calendar date (`YYYY-MM-DD`), `message` a comment, `image` an optional photo file name. `recipe.last_made` is derived, never written directly: creating or deleting an event recomputes it as the greatest `occurred_on`, falling back to null. Mealie's "Made this" shape (decisions.md row 41).
- `food.skip_shopping` is "on hand" (Mealie's `onHand`): water, salt, pepper, white and caster sugar, the cooking oils. `aisle` is its own table.
- Conversions are per food (decisions.md row 69): `food_conversion` reads "1 cup of plain flour is 125 g", one row per food per pair of units, both units cascading, and the food document carries them as `conversions`. `unit.standard_quantity` / `unit.standard_unit_id` keep the unit-to-unit conversions that hold whatever is being measured (1 l is 1000 ml). A cup of flour is 125 g and a cup of sugar is 220 g, so the food's rows are tried first and the unit's are the fallback.
- Quantities are stored as decimals. `unit.fraction` says whether to render ½ or 0.5.
- Images live on the disk volume: `DATA_DIR/images/<recipeId>.<ext>`, one per recipe, and `DATA_DIR/images/timeline/<eventId>.<ext>`, one per logged cook. `recipe.image` and `timeline_event.image` hold only the file name. Not in the DB.

## Scaling

- `factor = target_servings / recipe.servings`
- Linear ingredients multiply by `factor`, and so does `recipeYieldQuantity`. Fixed and null quantities do not.
- Timers and cookware never scale.
- Nothing scaled is ever persisted. A recipe stored with 0 servings has no factor and is returned as stored.
- Where it happens (decisions.md row 62): **on the client**. The recipe and cook loaders fetch the stored document once — `?servings=` is not a loader dep — and each page applies `scaledForServings(doc, servings)` from the search param, so − and + repaint without a request while the URL still carries the scale.
- `getRecipe({ slug, servings })` scales the same way on the server, for outside callers and for a URL opened cold. Both sides call the one pure function in `src/domain/recipes/recipe/scale.ts`, so they cannot drift.

## Shopping list

One list for the household, with no owner and no list table (decisions.md row 67): Mealie has many lists because it has many users and groups, and garnish has neither. `005_shopping.sql` builds it; the document is `src/domain/shopping/shopping.ts`, the repository `src/db/models/shopping/repo.ts`, the server functions `src/api/rpc/shopping.ts`.

- A line is a food line (`food_id`, with an optional `unit_id` and `quantity`) or a free-text line (`text`, "batteries"). One table holds both, as Mealie's `shopping_list_item` does.
- `position` is the list order over the whole list. It is not unique: a reorder rewrites every row in one transaction.
- `ticked` is the supermarket's only write, and the one write the app queues offline (M31.5). `updated_at` moves with every change.
- `shopping_item_source` is where a line came from — Mealie's `recipeReferences`, one row per contributing recipe: `recipe_id` while the recipe exists, plus `recipe_name`, `part_name`, `servings` and the `quantity` that source contributed. The names are copies, not joins, so an expanded line still reads "Lemon tart, Pastry, serves 4" after the recipe is renamed or deleted; `recipe_id` goes null with the recipe, the sources cascade with their line. `unit_id` is the unit that `quantity` is in (NULL: the line's own), and `plan_date` the meal plan day that asked for it (NULL from anywhere else); `025_shopping_source_unit_date.sql` adds both for the meal view.
- The document nests `food` (carrying its aisle) and `unit` as the recipe document does, and nests `sources` under their line. Writes send ids only — everything a line points at already exists, so the list never creates reference rows the way a recipe save does.
- Merging is the caller's job, not the table's: the repository appends what it is given. `mergeIntoList` (M31.2, pure, in `src/domain/shopping/shopping.ts`) is what merges an addition by `(food, unit)` into an unticked line and appends a source to it.
- Two views of the same lines, switched at the top of the page and remembered per device (`prefs.shoppingView`; decisions.md row 182). **Aisles**, the default: grouped by `aisle` in `aisle.position` order with unassigned last, each line with the dishes it is for in a quiet second line under it (`mealsOf`: "Lemon tart, Mon · Roast chicken, Wed"; decisions.md row 183), ticked lines sunk to a Ticked group with Clear ticked (`groupByAisle`). **Meals**: one group per dish, a recipe on a plan day (the same recipe on two days is two dishes), in day order, then recipes added from their own page, then Other for hand-typed lines and plain plan entries; a line two dishes share is a row under each showing that dish's share from its sources, with the whole line in the expansion, and a tick on either is a tick on the line; ticked lines stay under their dish (`groupByMeal`).
- Pack sizes (decisions.md row 184): `food_pack` (`026_food_pack.sql`) holds the sizes a food is sold in, one row per size, `unit_id` NULL for "each" (6 eggs). They are not on the food document; the list and Settings › Foods read them beside the foods (`listFoodPacks`). The line keeps the exact need, so merging is untouched, and the aisle view rounds it up as it draws: `packsFor` (`src/domain/shopping/packs.ts`, pure) converts each size to the line's unit through the food's conversions, drops a size it cannot reach, and picks the packs that leave least over, then the fewest: "400 g butter → 2 × 250 g". An arrow that only repeats the line ("1 can → 1 can") is left off. Not in the meal view, whose rows are shares, and not for an on-hand food. Sizes are edited in the food sheet in Settings › Foods (`src/app/features/settings/components/food/`). A starter batch (`starter-packs-1`, `src/db/seed/packs.ts`) gives common Australian sizes to starter foods that have none.
- A row does not open (decisions.md row 187, replacing rows 185 and 186): the tick box and the line — its text ticks it too — and under it the dishes it is for, each a link to its recipe (the source carries the live recipe's `recipeSlug`, read, never stored) with its own amount when dishes share the line ("Lemon tart Mon 200 g · Roast chicken Wed 150 g", `mealsOf`). Removing it is a trash icon on the hovered row with a mouse, and a swipe left onto a red Delete on a touch screen; each is displayed on one kind of screen only. Foods, their aisles and sizes are edited in Settings › Foods.
- A food with `skip_shopping` (on hand) is added already ticked, so it is on the list to see but not to buy: it joins an unticked line of its food if there is one, else its ticked line, else starts a ticked one (decisions.md row 175).
- Until unit conversions exist (M32), 1 cup flour and 300 g flour are two lines. Known and accepted.

## Meal plan

One plan for the household, with no owner and no plan table (decisions.md row 71), and **the day as the unit**: a day holds as many entries as it holds, in `position` order, and an entry *may* name its meal — breakfast, lunch or dinner — but usually names none (decisions.md row 100). `007_plan.sql` builds it, `012_planner.sql` adds the meal; the document is `src/domain/plan/plan.ts`, the repository `src/db/models/plan/repo.ts`, the server functions `src/api/rpc/plan.ts`.

- An entry is a recipe entry (`recipe_id`, with `servings` optionally overriding the recipe's own) or a plain line (`text`, "leftovers", "out"). One table holds both, as `shopping_item` does.
- `date` is a calendar date, `YYYY-MM-DD`, with the same GLOB check `timeline_event.occurred_on` carries. `position` is the order within that day, and is not unique: a move rewrites a day's rows in one transaction.
- `recipe_id` sets null rather than cascading: deleting a recipe must not silently empty a planned day, and the entry survives as the plain line it becomes.
- `meal` is nullable and NULL by default, and it labels rather than slots: the week strip is seven days, not seven days by three, nothing is drawn for an empty lunch, and `position` stays the only order within a day. Mealie's grid of meal slots is still the divergence, and its fourth value `side` is not adopted — a side or a snack is an untyped entry, since `side` is a kind of dish rather than a time of day. What reverses is only the "no entry type" half of row 71: stage 14's proposal needs an open slot to be a fact it can name.
- A week is the unit read: `week(monday)` answers seven `PlanDay`s, Monday first, **empty days included** — an empty Wednesday is part of the answer. Dates are arithmetic on strings in UTC (`addDays`, `mondayOf`, `weekDates`, `groupByDay` in `src/domain/plan/plan.ts`, pure).
- The document nests `recipe` with only what the week strip draws — id, slug, name, image — one select per week, not one per entry. An entry whose recipe has been deleted reads back with `recipe: null` and keeps its day. Writes send `recipeId`.
- No copied recipe name, unlike a shopping source: a plan is read for the week it names, not asked weeks later where a line came from.

## House style

The household's own voice for the steps (decisions.md row 78), kept as a list of short statements rather than a paragraph of prose. `010_style.sql` builds it; the document is `src/domain/recipes/style/style.ts`, the repository `src/db/models/style/repo.ts`, the server functions `src/api/rpc/style.ts`, and Settings has a **Style** tab over it.

- The import is faithful on purpose — stage 12's check rejects any changed word — so the restyle is a **second, separate pass**: the import's third stage when a model is configured (Source, Review, **Style**, Save; decisions.md row 119), and a saved recipe's Style page (`/recipes/$slug/style`) after that. The read keeps the author's words; the style is what the household chooses from them before anything is stored.
- It rewrites **steps only**. Ingredient lines, quantities, parts and metadata are frozen; what a restyle may not change is facts, so its check is on numbers and foods rather than on text.
- A statement is its whole sentence ("Keep the order of work: steps stay in the order the author gave them."), because the text is exactly what is read out to the model. Nothing in the code switches on a statement, so any of them may be reworded into the household's own terms.
- The prompt anchors the rewrite to the author's step boundaries — splitting and merging happen only where a statement asks — because told that steps "may be merged or split", every model tried turned seven steps into twenty. Step size is therefore a statement, and the seeded one is **one stage per step**: everything done at one pan or bowl until the next wait or the next pan, which is usually the author's paragraph. "One action per step" was tried in several wordings and every model read it as one verb per step, so it is not seeded; the lab's `--rules` file is where to try a different size.
- Quantities live in the ingredient row a step links to, not in the step's text. Each ingredient line in the prompt carries `(food: …)` naming its food, the statement says to call the ingredient by that name and to write a quantity only where the author did or where part of a row is used, and since the food name is what `suggestLinks` matches on, a rewrite that obeys links better than the author's steps did.
- Only parts with steps are sent. An import can leave the main body empty when every step sits under a heading, and a model given nothing to rewrite leaves the part out of its answer; `withEmptyParts` splices such parts back in as themselves, so the pairing holds.
- The facts check reads a bracketed aside with no unit in it — "(I use 2 wooden spoons)", "(Note 5 for slow cookers)" — as chatter rather than fact, since the no-chatter statement drops it on purpose; a bracketed time or temperature is still a fact.
- `bun run restyle <recipe> [--part <name>] [--model <a,b>] [--rules <file>] [--prompt]` tries the pass on one recipe from the author's kept steps and prints each model's rewrite with the check's verdict and step counts, writing nothing. A statement or prompt change is tried there on two models before it lands: the pass must read well whatever model is passed in, so a change that only one model follows is not a fix.
- `enabled` is the default tick for a run, not a lock: the Style space starts from it and every statement can be turned on or off for one recipe. `position` is the order they are numbered in, and is not unique — a reorder rewrites every row in one transaction.
- Seeded with eleven statements, one per theme (`src/db/seed/style.ts`), all on: step size, voice, chatter, ingredients, timing, parts, metric, labels, emphasis, the supporting line and preparation. One sentence per theme rather than the earlier fourteen because the finer list read as granular in Settings and the models followed a theme's one sentence as well as three. None of them tells the model to *keep* anything: conservation is the fixed line's job, above the guide, because a guide half made of guards asks for nothing and the recipe comes back unchanged (decisions.md row 112). Re-seeding matches an existing row by its whole text, case-insensitively, so an edited statement survives and is never duplicated — and a household's rewording means the seeded original comes back at the foot, where it can be switched off. The exception is a sentence this project itself reworded or folded into another: a seeded statement lists the old sentences in `was`, the first of them still present is given the new text in place, keeping the household's switch and order, and the rest are removed because what they said is now said there.
- The author's words are kept. The first restyle of a part copies the whole of it — its steps as `{title, text, summary}` and one note per ingredient row — into `part.source_part` (JSON, NULL until then) and never overwrites it, so "the original" stays the author's rather than the last rewrite; `restoreSteps` puts it back and clears the column. `recipe.restyled_at` is the stamp, shown as a quiet "Restyled" beside the source link, and cleared by a restore. Replaced steps get fresh ids and their links re-suggested (`suggestLinks`), so a step photo on a replaced step is lost.
- **Conservation** is **not** a statement. `FIXED_RESTYLE_LINE` leads every prompt and says the whole rule — temperatures, times and quantities copied exactly, and nothing else the recipe tells you lost either: every instruction, condition, cue, warning, shortcut and storage note still there afterwards, brackets at the end of a step included. It is enforced mechanically by the check, because it is not something anyone should be able to switch off.
- The check reads a recipe the way a cook does (decisions.md row 114): an imperial figure beside its metric twin in the same step is one quantity written twice and may be dropped; a step's own leading number is not a quantity; the ingredient rows join the facts on both sides, so a quantity the rewrite moved out of a step's text is still found in the row it moved into, while staying out of the foods check, where every row names its own food; and a lost `(if using)` is forgiven when the rewrite marked that ingredient `optional`. The food marker in the prompt is lower cased, because the model copies it verbatim and a Title Case library otherwise reads as "melt Unsalted Butter".
- The check is over the whole part, not its step text: `checkPart` reads every step's label, text and supporting line and every ingredient's note on both sides, so a sentence the pass *moved* into a field is conserved rather than reported lost. Beyond the numbers and the foods it gates on **conditions** — a dropped `if` or an `or until` narrowed to `until` changes what you do and is invisible to a count of numbers — and on the answered notes lining up with the part's rows. **Dropped words**, the author's content words the rewrite no longer uses, are reported and never failed, since a house style rewords by design (decisions.md row 112).
- **The Style space** (`src/domain/recipes/components/style/`) runs on arrival and shows the author's steps and the rewrite **side by side** — from `lg` three columns (ingredients, original, restyled), from `md` the two step columns under the ingredients, on a phone each step's two sides stacked; there is no view to flip (decisions.md row 167) — chosen **step by step** where the rewrite kept the author's step count and **whole** where it merged or split steps. The check is per part, so `partFindings` places each finding on the author's step whose words hold it, and that step starts on the original; a finding no step holds starts the whole part there. Because a rewrite can move a sentence between steps, the same check runs again over the assembled choice before Save and warns if the mix loses anything. A part's notes are the rewrite's whenever any of its rewrite is taken. An import saves through `createRestyledRecipe` (the author's recipe created, the choice applied over it, so Restore still has the original); a saved recipe through `applyRestyle`; a choice of nothing but originals writes nothing.
- The pass writes prose and arrangement, never rows. It answers three fields per step and one note per ingredient row, **positionally**: it is never shown a quantity, a unit or a food to rewrite, so a changed row is impossible rather than merely forbidden (decisions.md row 113).

## Planner

The household's own rules for what a good week looks like (decisions.md row 101), kept as the house style guide is kept: a list of short statements, each on or off, in the order they are read out. `013_planner_guide.sql` builds it and `014_planner_meals.sql` takes the meal switches back out again; the document is `src/domain/plan/planner/planner.ts`, the repository `src/db/models/planner/repo.ts`, the server functions `src/api/rpc/planner.ts`, and Settings has a **Planner** tab over it, between Style and Import and export, badged with the number of statements that are on.

- **The guide** is `planner_rule`, `style_rule`'s shape exactly — `id`, `position`, `text`, `enabled`, the two timestamps — because it is the same object read to a different pass. Two tables rather than one with a `guide` column: the guides are read, edited, seeded and reordered separately and nothing ever wants both, so a shared table would put a WHERE on every query and buy nothing. What is shared is the seed (`src/db/seed/statements.ts`, the match-by-text and `was` logic both guides go through) and the UI (`StatementList`, the rows and the add box both tabs render).
- Seeded with seven statements (`src/db/seed/planner.ts`), five on: nothing eaten in the last three weeks unless it is a favourite, produce in season here this month, quick weeknights with the long cooks at the weekend, variety across the week's proteins and cuisines, and leaning on favourites with one recipe brought back. Two are seeded off — two vegetarian dinners a week, and a big-batch dinner becoming the next day's lunch — because they are a household's choice rather than a default. Re-seeding matches an existing row by its whole text, case-insensitively, exactly as the style guide's does.
- **The meals** are a per-run choice, not a setting and not a table (decisions.md row 102). Since row 194 the run is Plan the week's first pass: dinner always, and "Also plan" Breakfast and Lunch above the weeknights, remembered on the device under `garnish.planner.meals`; the days are the week's open ones, so `garnish.planner.days` is no longer read. They were `planner_meal` from M39.2 until M39.7; the household's answer changes week to week, and a default in Settings was one more place to look before pressing Propose. They are a choice rather than a statement because the proposal is *built* from them — `proposalInput({ monday, dates, meals })` opens a slot per `(date, meal)` pair — rather than asked to weigh them, and they share their vocabulary with `meal_plan_entry.meal` (decisions.md row 100) so a slot means one thing throughout. `MEALS` in `src/domain/plan/planner/` is where the three are written down.
- **What is sent**: the enabled statements, numbered in order (`enabledRules`), plus the fixed lines of the run — today's date, the southern hemisphere, what a recipe's week means (`WEEK_LINE`: weeknight recipes for weeknights, weekend recipes for Saturday and Sunday, unless a statement says otherwise; rows 194 and 219), what its facets mean for a slot (`FACET_LINE`: a dinner is a main, a soup, a salad or a recipe with no course said, a building block is never planned on its own, a meal said is respected; row 209, and each library line carries the facets said, as `course: main; diet: vegetarian`), and the week's open slots, which are the chosen meals on each chosen day that has no entry for them. The facts of a run are not statements, for the same reason the restyle's "temperatures, times and quantities are never changed" is not one: nobody should be able to switch off the date.
- **What is checked**: the proposal is a proposal. Every recipe it names must be a real recipe, every slot it fills must be one of the open slots it was given, and the week is shown for review in Plan the week — Swap, Night off, Skip and the weekend's choice are the acceptance — so the model proposes and the household accepts; nothing is written to `meal_plan_entry` until it does. The plan is the household's, and a model never edits it behind them.
- `bun run propose [--week <monday>] [--days mon,tue] [--meals breakfast,dinner] [--model <a,b>] [--rules <file>] [--prompt]` builds the same input (`--meals` defaults to dinner, as the sheet does) from the live database and tries it on one or more models, printing each one's week as a table (day, meal, recipe, reason) with the check's dropped and unfilled counts and the time taken, writing nothing — the restyle lab's shape, over the planner's gathering rather than one recipe's steps.

## Backup and restore

Two pairs of words, kept apart (decisions.md row 131). **Backup and restore** are the whole household: a backup is everything the household made, and a restore *replaces* the database with it — never merges, never overlays — so afterwards the app is exactly as it was when the backup was taken. **Export and import** are one recipe at a time: export is a readable copy (`/api/recipes/:slug.json`, `.cook`), import adds a recipe through the review and never removes anything. Mealie draws the same line: Settings › Backups for the instance, recipe import and export apart from it.

**Taking one.** `bun run backup` writes `DATA_DIR/backups/garnish-backup-YYYYMMDD-HHmmss.zip` (UTC); Settings › Backup's **Download backup** sends the same file to the device from `GET /api/backup.zip` and keeps nothing on the server; only the CLI writes into `backups/`. It is read from the live database through the repositories, so it is consistent with what the app shows.

**Restoring one.** `bun run restore <file.zip>`, or an upload on Settings › Backup behind Mealie's confirm: the sheet names what will be replaced (recipes, cooks, plan entries, list lines) and Restore stays disabled until "I understand this replaces everything" is ticked. Either way:
1. The file is read and checked in full — zip, `garnish.json` against the schema, every reference resolved, the version known — before anything is touched. A failure names the problem and writes nothing.
2. A `.db` snapshot of the current database (`VACUUM INTO`, `backups/garnish-pre-restore-YYYYMMDD-HHmmss.db`) is taken, so a wrong file can be undone by hand. It is a safety net, not a backup the household chooses.
3. One transaction empties the household's tables and inserts the file's rows. The new images are written to a staging folder first, and once the transaction commits `images/` moves beside the snapshot (`garnish-pre-restore-…-images/`) and the staged folder takes its place, so the snapshot and its photos undo a restore together.

**Container.** A zip: `garnish.json` and the image files under the paths the JSON names. Images go in stored (they are already compressed), the JSON deflated.

```
garnish-backup-20261007-091500.zip
├── garnish.json
└── images/
    ├── <uuid>.<ext>            recipe images
    ├── steps/<uuid>.<ext>      step photos
    └── timeline/<uuid>.<ext>   cook photos
```

**Rules for `garnish.json`.**
- Keys are camelCase, the domain documents' names. Ids are the database's UUIDs, kept, so every link survives a round trip: an ingredient to its food, a food to the recipe that makes it, a plan entry or a shopping source to its recipe.
- Normalised: a row names a food, unit, aisle, tag or recipe by id, and the top-level list holds the one copy. Nothing is written twice, so nothing can disagree.
- Timestamps are ISO instants (`2026-10-07T09:15:00.000Z`), days are `YYYY-MM-DD`, quantities are numbers or null, text defaults to `''`, never null.
- An image is a path inside the zip (`images/steps/9b1c….jpg`) or null. An image the database names but the disk does not have is written as null.
- Lists are in a stable order (by `position` where there is one, else by name, else by date), so two backups of the same database differ only in `createdAt`.
- Derived values are left out: `recipe.lastMade` (from the timeline) and a food's or tag's usage counts.

**Shape.**

```ts
{
  garnish: {
    format: "garnish-backup",
    version: 1,                 // bumped only when a reader of the old shape would misread the new one
    createdAt: string,          // ISO instant
    appVersion: string          // src/lib/version.ts, for the record; not read back
  },

  aisles: { id, name, position }[],
  units:  { id, name, pluralName, abbreviation, useAbbreviation, fraction, portion,
            standardQuantity, standardUnitId }[],               // standardUnitId → units
  tags:   { id, name, slug }[],
  foods:  { id, name, pluralName, aliases: string[], aisleId, recipeId, skipShopping,
            conversions: { id, unitId, quantity, toUnitId, toQuantity }[] }[],
                                                                // aisleId → aisles, recipeId → recipes

  recipes: {
    id, slug, name, description, image,
    rating, favourite, recipeServings, recipeYieldQuantity, yieldUnitId, recipeYield,
    prepTime, performTime, sourceUrl,
    tagIds: string[],
    notes: { id, title, text }[],
    parts: {
      id, name,                                                 // '' is the unnamed main body
      ingredients: { id, quantity, unitId, foodId, note, originalText, fixed }[],
      steps: { id, title, text, summary, ingredientIds: string[], image }[]
    }[],
    createdAt, updatedAt
  }[],

  timeline: { id, recipeId, occurredOn, message, image, servings, createdAt }[],

  plan: { id, date, position, meal, recipeId, text, servings }[],    // meal: breakfast | lunch | dinner | null

  shopping: {
    id, position, quantity, unitId, foodId, text, ticked, createdAt, updatedAt,
    sources: { id, recipeId, recipeName, partName, servings, quantity }[]
  }[],

  styleRules:   { id, position, text, enabled, createdAt, updatedAt }[],
  plannerRules: { id, position, text, enabled, createdAt, updatedAt }[]
}
```

**Left out, on purpose.**
- Restyle originals: `part.source_part` and `recipe.restyledAt`. The backed-up steps are the recipe's current steps; a restored recipe reads as if it had never been restyled, and Restore original has nothing to offer.
- The MCP server's OAuth clients, grants and token hashes belong to the server and the clients it let in. A restore leaves them as they are, so a connected assistant stays connected.
- Timer alerts: push subscriptions, the VAPID key pair and pending alarms belong to the server and the devices that subscribed to it, not to the household's data. A restore leaves them as they are.
- Bookkeeping: the `migration` and `seed_batch` tables. A restore runs into a database already migrated and seeded, and keeps that database's own record of both.

**Reading it back.** A version newer than the reader knows is refused by name; an older one is read through an upgrade step per version. References run both ways (a food may name the recipe that makes it, a recipe's rows name foods; a unit may name its standard unit), so the insert runs in two passes: the lists in the order above with `food.recipeId` and `unit.standardUnitId` held back, then those two set once every row exists. A reference to an id the file does not hold fails the check in step 1.

## API

- **Server functions** (`createServerFn`) for everything the app itself calls, one file per resource in `src/api/rpc/`. Input validated with the shared zod schemas. Reads use `method: 'GET'` so they are cacheable; writes are `POST`.
  - `recipes`: `listRecipes({ q?, tag?, tags?, match?, foods?, favourite?, facets?, neverMade?, sort?, dir?, seed? })` (card summaries), `getRecipe({ slug, servings? })`, `createRecipe(doc)`, `updateRecipe({ id, doc })`, `duplicateRecipe({ id })`, `setFavourite({ id, favourite })`, `setFacets({ id, facets })`, `deleteRecipe({ id })`.
    - Filters combine with AND: name substring, tag slugs (`match: 'any' | 'all'`, default any; the older singular `tag` folds in), food ids, favourites-only.
    - `sort` is `name | created | updated | lastMade | rating | random`, with `dir` defaulting per key and nulls last. `random` takes a `seed` so the same URL keeps the same order. Unsorted is newest first.
    - Summaries carry what the card draws: name, slug, image, rating, tags, `favourite`, `lastMade` and `totalTime`.
  - `timeline`: `listTimeline({ recipeId })` (newest first), `createTimelineEvent({ recipeId, event })`, `deleteTimelineEvent({ id })`. Both writes recompute `recipe.last_made`.
  - `shopping`: `listShoppingItems()`, `addShoppingItems({ items })`, `updateShoppingItem({ id, ...patch })`, `tickShoppingItem({ id, ticked })`, `removeShoppingItem({ id })`, `clearTickedShoppingItems()`, `reorderShoppingItems({ ids })`. No list id anywhere: there is one list.
  - `plan`: `listPlanWeek({ monday })` (seven days), `addPlanEntry({ date, recipeId?, text, servings?, meal? })`, `updatePlanEntry({ id, ...patch })`, `movePlanEntry({ id, date, position })`, `removePlanEntry({ id })`. No plan id: there is one plan. `meal` is optional on a write and defaults to null.
  - `planner`: `listPlannerRules()`, `createPlannerRule({ text, enabled?, position? })`, `updatePlannerRule({ id, ...patch })`, `deletePlannerRule({ id })`, `reorderPlannerRules({ ids })` — the style guide's five, over the planner guide — and the proposal's own two: `proposePlanWeek({ monday, dates, meals })` (at least one of each, every date a day of that week) and `applyPlanProposal({ entries, servings? })`, where `servings` is the sheet's "how many are eating", written onto every entry (null keeps each recipe's own).
  - `ai`: `aiAvailable()`, the one gate for every model-backed feature (import, restyle, planner): a key is the whole of it; `getAiStatus()` and `testAiConnection()` for Settings' AI tab.
  - `foods`, `units`, `aisles`, `tags`: `list({ q? })`, `create`, `update`, `delete`, `findOrCreate({ name })` each, e.g. `listUnits`, `findOrCreateTag`. Input schemas in `src/domain/recipes/reference/reference.ts`.
    - `listFoodSummaries()` lists every food as a `FoodSummary`, for the home filter's picker, which needs no aliases or conversions.
    - `usingFood`, `usingUnit`, `usingTag` list the recipes a delete would touch (`recipes.query({ by: "food" | "unit" | "tag", id })`); the confirm dialog shows them.
    - `mergeFood`, `mergeUnit`, `mergeTag` repoint references onto a target and delete the source in one transaction. `reorderAisles` writes a new `position` order.
  - `fetchImage({ url })` pulls the image a URL import found server-side, through the same sniffing and cap as the upload route, so the editor never fetches cross-origin from the browser. The editor's own paste-an-image-URL field is gone (decisions.md row 79); the picker takes a file only.
  - Every chain carries `notFoundMiddleware` (`src/server/core/fn.ts`), which rethrows a repository `NotFound` as the router's `notFound()`; loaders render it through `notFoundComponent`. It is a middleware rather than a wrapper around `createServerFn` because Start's compiler must see the literal chain (decisions.md row 36).
  - Deletes return the removed row, as Mealie does.
- **Server routes** under `/api/*` only for callers outside the app, and later import hooks. Field names follow Mealie where the concept exists.
  - `GET /api/health` → `{ "ok": true, "version": "1.2.3", "commit": "940422d" }`. The Docker healthcheck probes it; the version and commit are the build's (`src/lib/version.ts`, decisions.md row 165).
  - `POST /api/recipes/:id/image`: multipart, file in the `image` field, png/jpeg/webp/gif sniffed from the bytes, 20 MB cap. Replaces the recipe's file and answers `{ image: "<id>.<ext>" }`.
  - `GET /api/images/:file`: the stored bytes. Names that are not `<uuid>.<ext>` are rejected before touching the filesystem.
  - `POST /api/timeline/:id/image` and `GET /api/images/timeline/:file`: the same pair for a logged cook's photo, under `images/timeline/`.
  - `POST /api/recipes/:id/steps/:stepId/image` and `GET /api/images/steps/:file`: the same pair again for one method step's photo, addressed by the recipe that owns the step (another recipe's step id is 404), under `images/steps/` (M35.1). The file is named for the step id, and the name rides in the recipe document beside the step's text, so the save that re-inserts every step keeps it. A step the recipe has never saved has no row and is a 404, which is what the editor reports as "save first".
  - `GET /api/recipes/:slug.json`: one recipe's document as the editor saves it, with `image` as its `/api/images/` URL. 404 for an unknown slug.
  - `GET /api/backup.zip`: a fresh backup of the whole household as a download, `garnish-backup-YYYYMMDD-HHmmss.zip` ([Backup and restore](#backup-and-restore)).
  - `POST /api/restore`: multipart, the backup in the `file` field, 500 MB cap. With `?check=1` it reads and checks the file and answers `{ createdAt, backup, current }` (what it holds beside what the database holds now) and writes nothing; without, it replaces the household's data and answers `{ createdAt, counts, snapshot }`. A refused file is 400 `{ problems }`, every reason listed, and nothing written.
  - `POST /api/import/file`: multipart, the export in the `file` field, 100 MB cap. Reads a Mealie backup zip or one recipe's JSON (`src/domain/recipes/import/sources/mealie.ts`, decisions.md row 73), or a Tandoor export — its zip of per-recipe zips, one recipe's zip, or a bare `recipe.json` (`src/domain/recipes/import/sources/tandoor.ts`, M34.4) — told apart by shape rather than by file name, and answers `{ recipes: [...] }` for the review step. A Tandoor step becomes a part, owning its ingredients and linking them to its own instruction; a nested-recipe step becomes a food row when the child came with it and a text line when it did not. Nothing is written — the review is what decides and the editor's Save is what writes.
  - `POST /api/mcp`: the MCP server ([MCP](#mcp)). Bearer token required; without one, 401 naming the protected-resource metadata.
  - `GET /.well-known/oauth-protected-resource[/api/mcp]`, `GET /.well-known/oauth-authorization-server`, `GET|POST /api/oauth/authorize`, `POST /api/oauth/token`, `POST /api/oauth/register`, `POST /api/oauth/revoke`: the OAuth server in front of it. Always on; every address they name is built from the request.
  - `GET /api/recipes/:slug.cook`: the recipe as a Cooklang file (`src/domain/recipes/recipe/cooklang.ts`'s `toCooklang`), `text/plain; charset=utf-8`. 404 for an unknown slug, same as the JSON twin. The recipe menu's "Copy as Cooklang" reads the same function client-side rather than fetching the route.
  - The `.json` and `.cook` suffixes are path suffixes, not params: the file routes are named `export[.]json.ts`, `{$slug}[.]json.ts` and `{$slug}[.]cook.ts`, where `[.]` escapes the dot the file convention would otherwise split on and the braces end the param.
- Recipe read returns the full nested document: recipe, parts, ingredients, steps, notes, tags. `favourite` is part of it; timeline events are read separately.
- Recipe write accepts the same document. One transaction, whole recipe replaced, `id` and `created_at` kept. Slug derived from the name, de-duplicated with a suffix.
- Route loaders are the only read path and call server functions directly; there is no client cache and TanStack Query is not added. Mutations go through `src/lib/mutate.ts`: call the server function, then `router.invalidate()` so every active loader re-runs.

## MCP

An AI assistant reads and changes the household's recipes, shopping list and meal plan through an MCP server at `/api/mcp` (decisions.md row 181). Nothing in it is particular to one assistant: any MCP client that does OAuth connects — Claude, ChatGPT, or another. Assistants on the web and the phone call it from their makers' servers (claude.ai's from Anthropic's), so this one door faces the internet, through a tunnel the household runs; the paths to forward are `/.well-known/oauth-*`, `/api/oauth/*` and `/api/mcp`, and nothing else.

- **Always on, addressed by the request.** The pairing code is the guard, so there is no switch. The OAuth issuer and every address in the metadata come from the origin each request reached (`requestOrigin`: the `Host` or `X-Forwarded-Host` header, and https when `X-Forwarded-Proto` says so), so a client through the tunnel is answered in the public address and one on the LAN in the LAN's, and a token is bound to the one it was issued at. A forged header changes only the answer to the request that forged it. `GARNISH_PUBLIC_URL`, optional, pins the origin instead, for a tunnel that does not send `X-Forwarded-Proto`; a wrong value is ignored and Settings says why. Settings › MCP shows the address the browser opened garnish at — on the LAN, since the tunnel does not carry the app — or `GARNISH_PUBLIC_URL` when set.
- **The pairing code.** What the consent page asks for: twelve characters of Crockford base32 (`K7QF-M2XP-9RTD`, 60 bits), made by garnish the first time anything asks (`mcp_pairing`, one row, 024_mcp_pairing.sql), so there is nothing to configure. Settings › MCP shows it hidden, with Show, Copy and Regenerate, and reads itself again when the window comes back into view, since connecting happens in another app. Every Allow replaces it — a conditional update on the code just checked, so two Allows on one code cannot both spend it — and a code that has been typed is never good twice. Regenerate replaces it too; neither disconnects anyone. Typed in any case, with or without dashes, O, I and L read as 0 and 1.
- **The flow.** An MCP request without a token gets 401 naming `/.well-known/oauth-protected-resource/api/mcp`, which names the authorization server, whose metadata names the endpoints. The client registers (RFC 7591) or brings a Client ID Metadata Document, its client_id being the document's https URL (fetched only from a public host, no redirects, 16 KB, cached an hour). The person's browser opens `/api/oauth/authorize`, a plain server-rendered page (not an SPA page: the tunnel does not carry the app's assets) naming the client and, for a metadata client, its host, with a box per scope, the pairing code, Allow and Deny. Allow returns a code (two minutes, once, in memory) to the client's registered redirect; the client trades it with its PKCE verifier for an access token (one hour) and a refresh token (thirty days, replaced on each use).
- **Tokens.** Stored only as SHA-256 hashes, bound to `/api/mcp` (RFC 8707). A grant is one Allow; Disconnect in Settings deletes it and its tokens. A spent refresh token presented again after thirty seconds is taken as stolen and revokes the grant.
- **Limits.** Ten wrong pairing codes a minute stop the consent page checking until the minute is out, for everyone (behind a tunnel every caller looks alike), short so that nobody can lock the household out; thirty registrations an hour; thirty token requests a minute per client. Registered clients nobody allowed in are swept after a day.
- **Tools.** One MCP server per request (stateless, JSON responses), holding the tools the token's scopes allow — `read`: search_recipes, get_recipe, list_foods, list_units, list_tags, get_house_style, get_shopping_list, get_meal_plan; `write`: create_recipe, update_recipe, add_to_shopping_list, tick_shopping_item, add_to_meal_plan; `delete`: delete_recipe, remove_shopping_item, remove_from_meal_plan. Each carries MCP's read-only or destructive hint. The recipe document carries `kind` and `facets`, each layer an array of its fixed values; a write's `facets` changes only the layers it sends (a layer sent as `[]` is cleared), and search_recipes takes one filter per layer, any of its values, all layers given (decisions.md row 209).
- **The recipe a model writes** (`recipeDocument.ts`) is not the editor's document: an ingredient is a line as a person types it, parsed by `parseIngredient` against the household's units and foods (name, plural, other names), and a step is its text. A line may also name its food (`{ text, food }`, the household's name for it), which then wins over the reading; a name the household lacks is refused (decisions.md row 222). A short unmatched food name (four words or fewer) becomes a new food and a longer one a text line, and the answer lists both. No word of a line is lost: a word read as a unit the household lacks leads the note (row 221). An edit sends ids from `get_recipe`; a row whose id and text are unchanged is kept whole (its food, links and photo), and fields left out keep their values. Steps with no links get `suggestLinks`'s.
- **Before a delete** a backup zip of the household goes to `backups/garnish-before-claude-*.zip`, at most one per ten minutes.

## PWA

- Installable: `public/manifest.webmanifest`, SVG and PNG icons drawn from the brand tokens, Apple metas in the root route.
- Service worker: hand-written (`src/sw/worker.ts`), no workbox. `src/sw/plugin.ts` bundles it with `Bun.build` and emits `sw.js` as an asset of the client build, because Nitro serves static files from a manifest baked at build time and a file dropped in afterwards is a 404 (decisions.md row 37). Registered in production only (`src/lib/sw.ts`); dev has no `/sw.js`.
- Policies: navigations go to the network and fall back to the cached shell; built assets and `public/` are cache-first (precached at install); `GET /_serverFn/*` and `/api/images/*` are network-first and stored on success, so a recipe read while online opens offline. Two caches: a versioned precache replaced on every deploy, and one data cache that survives deploys.
- Updates are offered, not taken: a new worker installs and waits, because activating deletes the old precache and would pull the running page's chunks out from under it. The page notices the waiting worker (`watchForUpdate` in `src/lib/sw.ts`, over `registration.waiting` and `updatefound`) and raises a sticky notice with a **Reload**; that posts `SKIP_WAITING` (`src/sw/message.ts`, the one message the two sides share), the worker takes over, and `controllerchange` reloads the page — in every open tab, once each. A first install has nothing to wait behind, so it activates and claims the page as before. The version is a content hash of the worker bundle (`versionOf` in `src/sw/plugin.ts`), not `package.json`: the precache list is inlined in that bundle, so any changed asset changes the worker's bytes, which is what the browser compares.
- Writes are never attempted offline. `useOnline` shows a notice in the editor and disables Save.
- Timer alerts (decisions.md row 111): a phone freezes a backgrounded app, so the page's toast at zero only reaches a page that is open. Settings › Alerts subscribes the device to Web Push (`src/lib/push.ts`, `usePushAlerts.ts`) against the server's VAPID key (`src/server/push/vapid.ts`, made once and stored), and every timer write on the page also tells the server (`syncAlarm` in `useTimers.ts`, through `src/api/rpc/push.ts`): a running timer is an alarm at its end, a pause or dismiss drops it. The alarm clock (`src/server/push/alarms.ts`) sends the push at zero through the device's push service; the worker shows the notification and a tap opens the timer's page (`src/sw/push.ts` is the payload both sides read). The page's own toast still rings, so an open app hears both. iOS needs the app on the home screen; the server needs outbound HTTPS to Apple's and Google's push services; a `PUSH_CONTACT` variable overrides the VAPID subject. `web-push` is the one dependency, for the VAPID signature and the aes128gcm encryption.

## Persistence rules

- `DATA_DIR` (default `./data`) holds `garnish.db`, `images/` (with `images/timeline/`) and `backups/`. It is created on boot if missing.
- Migrations are numbered SQL files in `src/db/migrations/`, applied in order by `migrate.ts` beside them, each in its own transaction with its `migration` row. They run at boot and via `bun run migrate`. The built server has no source tree, so `src/server/core/db.ts` inlines them with `import.meta.glob` (decisions.md row 38); the CLI reads the directory. Opening a database is separate (`src/db/connection/open.ts`), so backing up or seeding does not pull the runner in.
- Each domain folder under `src/db/models/` has a `schema.ts` declaring its tables in TypeScript, and the repositories import the tables they touch directly — there is no barrel, because Drizzle's `schema` option only powers the relational query API (`with:`), which nothing uses. `drizzle.config.ts` and the drift test find the tables with a glob. It is a mirror, not a second migration source: the SQL files still build the database, and `test/db/drift.test.ts` migrates a real one and fails if the two disagree on tables, columns, types, nullability or primary keys. A new migration is written by hand or generated with `bun run db:generate` (drizzle-kit writes to `.drizzle/`, which is gitignored), reviewed, then copied into `migrations/NNN_name.sql` — generated SQL is never applied as-is, because Drizzle cannot express the `COLLATE NOCASE` the name columns rely on. `bun run db:diagram` draws the schema the migrations build as `.drizzle/schema.html`, to look at rather than read; a reference kept in JSON goes in its `SOFT_REFERENCES` so the page shows it as one the database does not hold.
- Repositories query through Drizzle rather than hand-written SQL, so row types come from the schema instead of being restated per file. The store, the handle and its lifecycle are unchanged: Drizzle wraps the connection `openDatabase` returns.
- One process-wide handle (`getDb()`), opened lazily, migrated and seeded once, retried on failure. It is synchronous — `bun:sqlite` is, and the bundled migrations need no IO — so a repository module can export `lazy(getDb, tagRepository)` as its default, built on first use and kept per handle: server functions and API handlers import that and never see the handle (decisions.md row 87). Only tests and the CLIs call the factory with a handle of their own. The `import.meta.glob` that bundles the SQL sits inside `bundledMigrations()` because the `seed` and `dev:seed` CLIs import repositories under plain Bun, where the glob does not exist.
- Backup is the zip of [Backup and restore](#backup-and-restore): `bun run backup` writes `DATA_DIR/backups/garnish-backup-YYYYMMDD-HHmmss.zip` (UTC), and `bun run restore <zip>` replaces the household with one, keeping the database as it was as `backups/garnish-pre-restore-YYYYMMDD-HHmmss.db` (a `VACUUM INTO` copy) first. README.md has the steps, and how to put a snapshot back by hand.
- The database is the only store. Backup and restore move all of it; export moves one recipe ([Backup and restore](#backup-and-restore)).
- Dev data is a separate thing from the seed and never ships: `.dockerignore` excludes `src/db/dev` from the build context, which is also why the reset is its own script rather than part of the server entry — `src/server.ts` cannot import a directory the image build does not carry.
- `bun run dev:seed` is a clean slate in three steps: wipe `DATA_DIR`'s database, its WAL sidecars and `images/` (`wipe.ts`; backups are left alone); migrate and run the same `seed()` the server runs on every start, dev or not, so dev looks at the reference data a real install has rather than a parallel set; then apply the dev library. Deleting the file rather than the rows is deliberate — it takes the schema with it, so a migration edited in place is re-applied instead of skipped for having a `migration` row already. It refuses to run under `NODE_ENV=production`.
- `bun run dev` starts Vite and leaves the database alone, so recipes added or imported in dev survive a restart. `dev:seed` is run by hand when a disposable, known state is wanted; nothing runs it automatically.
- The dev library is twenty hand-written recipes a household might really keep, in the house style (decisions.md row 216): weeknight regulars cooked often, weekend projects, a soup, a salad, baking, a dessert and two building blocks linked as sub-recipes, with a few never made and unrated. Between them they use every feature the document has. Ages, cook-log dates and a week of plan entries are kept as days before or after the run and dated from the day it runs, so Home always opens on a live week. Every recipe and some steps carry a real photo of the dish (`src/db/dev/images/`, found on Openverse and Wikimedia Commons under CC0, public domain, CC BY or CC BY-SA, credited in `CREDITS.md`), because a page is judged on how it looks and coloured squares made every page look wrong.
- Seed: fifteen metric and common imperial units, matched by name case-insensitively so re-seeding never overwrites edits. Runs at boot and via `bun run seed`. `src/db/seed/` is what every database gets and nothing else: the data (`units.ts`, `foods.ts`, `foodPlurals.ts`, the two guides) apart from the inserting (`seed.ts`, `starter.ts`) and the CLI (`cli.ts`). Recipes are never seed data: `bun run dev:sample` adds three hand-written demo recipes (one with three parts), idempotent by slug and wiping nothing: one is favourited, one carries a source URL and one has two timeline events, so every screen has data.
- Starter foods (decisions.md row 121): every database begins with twelve aisles in walking order and some 750 foods in them (`src/db/seed/foods.ts`), so an import reads against a real vocabulary from the first recipe. The list was drawn from the ingredient lines of about 2,000 recipes on Australian and British sites, checked against a US cookbook corpus, and scored against 400 recipes it was not built from: three lines in four match a food with no review. Names are the Australian shelf's (caster sugar, capsicum, coriander, prawn); aliases carry the US and UK words, other spellings and plurals; and a compound is a food of its own whenever its head is one (lemon juice beside lemon, garlic powder beside garlic, egg yolk beside egg), because the matcher keeps the longest name a line starts with and a lone head would swallow it. No brands, no prepared dishes. Only water and the salt-and-pepper line skip the shopping list.
- A line that gives its amount twice — "250g / 8oz green beans", as "500g (1 lb)" does in brackets — keeps one as the amount and the other as the note: the metric one, else the first (a cup counts as metric). The second amount is only read when the slash is followed by an amount and a known unit with words after them, so `salt/pepper` and `1/2` are untouched.
- The parser is measured against `test/fixtures/ingredients/benchmark.ts`: real lines from the same corpus, each labelled with the quantity, unit and food it should read as, and the decisions those labels take written at its head. `test/domain/recipes/ingredient/benchmark.test.ts` is a ratchet — a line read right must stay right, and a line marked `known` must stay wrong until the fix that mends it takes the mark off — and `bun run bench:ingredients` prints the score per category.
- The starter set is a batch, applied once per database and recorded in `seed_batch` (`starter.ts`), not re-inserted by name on every start as units are: foods are renamed, merged and deleted far more than units, and a merged-away food that came back each morning would undo the merge tools. The household's rows win: an existing aisle is reused by name; a starter food is skipped when an existing food already answers to its name, and one that goes in leaves out any plural or alias an existing food answers to; an existing food with the starter food's own name gains the aliases nothing else claims. A later addition to the list is a new batch with a new name. Dev data defines no units, aisles or foods of its own: both the sample and the library's recipes name the seed's through `src/db/dev/references.ts`, which throws for a name the seed does not have, so a dev recipe links to the seeded row rather than making a second one beside it (decisions.md row 129).
- A second batch, `starter-foods-2` (`foodPlurals.ts`, decisions.md row 128), corrects the first one's plurals once after it: foods counted by the piece take a singular name with the old one as their plural, and an alias gains its other number. Each correction applies only where the food is still as the first batch left it. `correctedStarterFoods()` is the list a new database ends up with.
- Locale: metric, en-AU spelling. Imperial units available, never default.

## Deploy

- Everything Docker is in `docker/`, and the compose file there is the canonical way to run and deploy: `cd docker && docker compose up -d`.
- Two-stage `docker/Dockerfile` on `oven/bun:1.4.2` (install and `bun run build`) then `oven/bun:1.4.2-slim` with only `.output/`. `bun:sqlite` is built into Bun, so nothing else is installed at runtime. The build context is the repo root; `docker/Dockerfile.dockerignore` beside it trims the context (BuildKit reads the ignore file named after the Dockerfile).
- `DATA_DIR=/data` is the volume; `PORT=9988` (garnish's port everywhere, decisions.md row 118), `HOST=0.0.0.0`, `BUN_JSC_useJIT=0` (JavaScriptCore interprets rather than compiles: about 110 MB under load instead of about 200, decisions.md row 188). Runs as root, like Mealie's default, so a bind-mounted host directory needs no ownership setup.
- `HEALTHCHECK` fetches `/api/health` with Bun itself (the slim image has no curl).
- `.github/workflows/docker.yml` publishes the image to `ghcr.io/<owner>/<repo>` on every push to `main` (tagged `latest`, by the new version and by commit sha) and every `v*` tag (tagged by version); pull requests build without pushing. A `test` job (`bun install --frozen-lockfile`, `bun run check`, `bun run test`, `bun run lint`, on the Bun the image is pinned to) gates the `image` job, which builds `linux/amd64` and `linux/arm64` under QEMU with the Actions cache. `test/docker/workflow.test.ts` holds the contract.
- Versions are the workflow's, not a hand edit: on a push to `main` the `image` job runs `bun run version:next` before the build, which reads the commit messages since the last `v*` tag and advances `package.json`'s version by what they ask for — `feat` a minor, a `!` header or a `BREAKING CHANGE` footer a major, anything else a patch (`scripts/version.ts`, pure and tested). The build inlines that version, and once the image is published the bumped `package.json` is committed back to `main` as `chore(release): vX.Y.Z [skip ci]` with a matching annotated `vX.Y.Z` tag — annotated and named on the push, since `git push --follow-tags` ignores a lightweight one — which `gh release create` then publishes as a GitHub release. Its notes are the same commits, written by `releaseNotes` in the same script (decisions.md row 189): Breaking changes, Features, Fixes and performance, Other changes, each line the commit's subject under its scope, `chore`, `test`, `ci`, `docs` and `build` left out; `--generate-notes` adds GitHub's compare link after them. `[skip ci]` keeps the bot's own commit from starting the workflow again, and a `concurrency` group keeps two runs from racing for the version. A version is only spent on an image that published.
- The version reaches the code through `vite.config.ts`'s `define`, inlined as `__GARNISH_VERSION__` and read as `VERSION` from `src/lib/version.ts` — no `package.json` in the server bundle to keep in step, and `0.0.0-dev` outside a vite build. The commit beside it is `__GARNISH_COMMIT__`, read as `COMMIT` — `GARNISH_COMMIT` (the workflow's build argument, since the image's context has no `.git`), else git's short hash, else empty — and `buildLabel()` joins the two as `1.4.0 (940422d)` (decisions.md row 165). `GET /api/health` answers with both; Settings prints the label at the foot and in Diagnostics, and every error view under its message. The service worker is unaffected: it still compares its own content hash (decisions.md row 94), not this string.
- `docker/docker-compose.yml`: one service `garnish` on `image: ${GARNISH_IMAGE:-ghcr.io/sixthshift/garnish:latest}` — nothing is built on the running machine; set `GARNISH_IMAGE` to run a local build — port 9988 published, host folder `${GARNISH_DATA_DIR:-./data}` bind-mounted at `/data`, `restart: unless-stopped`.
